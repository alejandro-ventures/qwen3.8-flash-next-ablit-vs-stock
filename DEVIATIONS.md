## D1 (2026-11-07, before any B data): H4 gate uses the 50 non-thinking JSON tasks only
Observation (A0, stock `fd3f43e`): all 20 thinking-mode (profile JT) schema-JSON tasks returned schema-valid output with the wrong value (value-copy failure; reply example withheld), 0/20 correct, while the 50 non-thinking tasks gave 50/50 correct. A gate on all 70 tasks would be dominated by this engine behaviour in both arms and say nothing about the overlay.
Change: H4 compares unique failed tasks among the 50 non-thinking tasks (Clopper-Pearson bound with n=50, about 5.8%). The 20 thinking-mode tasks are reported separately as an engine observation (A0 vs A1 vs B).
Reason: seen on A0 only, before B data; no outcome-dependent choice about the overlay. Implemented in `analysis/compare.py`.

> **Correction note (2026-11-10).** The original D1 description incorrectly called the illustrated value-copy failure malformed JSON. This export corrects that classification; the task-success counts and the pre-B choice of the H4 endpoint are unchanged. Fresh synthetic checks likewise found schema-valid JSON with wrong copied values, not a syntax failure. See [findings/thinking_json_schema.md](findings/thinking_json_schema.md).


## D2 (2026-11-07, before any B data): speed aggregation
`bench_streams.py` prints only the median of its repetitions, not the individual repetitions, so the protocol's "bootstrap over 7 repetitions per session" cannot be computed from its output. Change: per session, the decode part (`--decode-only --streams 1,5 --reps 7`) is run 3 times (3 medians per condition per session, 6 per arm), the full run (prefill included) once. The arm value is the median of its 6 medians; the ratio B/A with a 90% percentile bootstrap CI over the 6+6 medians (resampling medians within arm). Fewer than the planned resamples are informative; the interval mostly shows session-to-session spread, which is the relevant uncertainty.

> **Correction note (added at export, 2026-11-10; the text above is unchanged).** The statement that the interval "mostly shows session-to-session spread" was withdrawn after the data existed (D13, item 4): the six values per arm are three medians within each of two sessions, so the interval reflects within-session repetition only; two sessions per arm cannot characterise restart-to-restart variability.

## D8 (2026-11-08): contamination rule for regular steps
Trigger: B1 halted because step bfcl was flagged contaminated twice (2/11 polls). Every flagged poll was running=4, waiting=1, harness_inflight=4: no request beyond the harness own ever executed; the extra waiting request is the admission queue while one request is replaced by the next. BFCL is short (about 11 polls), so one such poll exceeds the 5% threshold. Applying the old rule to A1 traffic would flag bfcl 3/12, aux 1/2, lc 6/150.
Change (made AFTER B data existed, triggered by a halt, applied symmetrically to every session including A1): for regular steps a poll is contaminated only if running > harness_inflight (a foreign request executing) or (waiting > 0 and running >= 5, a genuinely full server). Error polls still count. Layer 1 and speed rules, the 5% threshold and the one-rerun rule are unchanged.
Analysis commitment: report, as a sensitivity check, results with every step that would have been flagged under the original rule (any session) excluded, so readers can see D8 does not drive the conclusions.
Code: driver commit ff5d3fee0826 -> bb273ba498b0 (the driver's contamination() function and its D8 unit test; the driver is not part of this export). The pin in control/state.json was moved by hand; runs/B1/bfcl.jsonl archived as bfcl.contaminated2.jsonl (bfcl.contaminated1.jsonl kept) and bfcl rerun under the new rule; other B1 steps kept.

### D8 addendum (2026-11-08, after the reviewer's review: ACCEPT WITH CHANGES)
- D8 is a relaxed heuristic with known blind spots, not a proof that no foreign request ran. It can miss a foreign request that runs while the harness queues (e.g. running=4/waiting=1/inflight=4 read as 3 harness + 1 foreign executing), and both the old and new rules miss traffic between 30 s polls and a foreign request that replaces a finished harness request between polls. The admission-queue explanation for the observed (4,1,4) polls is UNVERIFIED (five server-side requests versus four harness-open requests also fits counter timing); it is the working explanation, not a finding.
- Timeline: A1 (PC harness, collected before the unattended driver existed) recorded traffic but had no halt rule; its bfcl (3/12) and aux (1/2) polls exceeded 5% under the old rule without a halt or rerun, and are kept as collected. B1 halted on bfcl; D8 was decided and deployed afterwards (about 10 minutes after the halt). At the time of the decision no B1 score had been computed or read by the orchestrator; the driver had scored and judged A1 but the orchestrator had not looked at A1 scores.
- Attempt selection (fixed now): every attempt is preserved (bfcl.contaminated1.jsonl, bfcl.contaminated2.jsonl, bfcl.jsonl); the result used in analysis is the LAST attempt of a step.
- Sensitivity analysis (specified now, before B data is analysed): a step-attempt is flagged under the original rule if more than 5% of its polls are flagged. Report (a) a session x step x attempt table of poll counts under both rules, including error polls, reruns and which attempt supplies the result; (b) the headline results with every benchmark flagged under the original rule in any session excluded from ALL four sessions (matched), with effect estimates, uncertainty and retained coverage; (c) speed results restricted to attempts with zero original-rule flags. B1 lc has few polls so far only because it had not run yet when this was written (A1 lc: 150 polls).
- Open code items, deliberately NOT changed on the second host (a change would move the pin again): the code comment and unit test wording overclaim ("nothing foreign executing"; the inflight=5 test is synthetic), missing waiting/harness_inflight counters silently count as 0, and there are no separate test cases for lc concurrency, masked-foreign patterns or missing telemetry. Escalated to the orchestrating AI session for a decision.

## D11 (2026-11-09): scoring environment, IFEval seeding, mbpp-239 (found while re-scoring on the PC after collection)

The unattended driver scored every session on the home server; the same raw files were re-scored on the client machine (`analysis/score.py`). Comparing the two found 10 per-item differences across 5 sessions x 3,124 scored items, all in two places:

1. **IFEval checker nondeterminism.** The vendored IFEval checker calls `langdetect` without a seed, so instructions such as `change_case:english_lowercase` score nondeterministically: the same stored reply returned 0 or 1 across 12 repeated calls (ifeval-1122: 5 of 12 were 1; ifeval-1843: 1 of 12). Fix: `analysis/score_det.py` sets `DetectorFactory.seed = 0` and then runs the unchanged scorer. All five sessions were re-scored with it, in one environment; those scores are the headline (`analysis/scores/`). The unseeded PC scores (`analysis/scores_unseeded/`) and the second host's scores (`analysis/scores_altenv/`) are kept as sensitivity rows. This noise (about 1-3 of 541 items per session) existed in the second host's scores for every session, so it is part of the earlier-observed run-to-run disagreement of 0-2 items; with the seed fixed, the remaining A1-vs-A2 and B1-vs-B2 ifeval disagreements are 1/1 and 1/0 items (genuine reply differences), everything else is 0/0.
2. **mbpp-239 and the 30 s code time limit.** The second-host scorer scored mbpp-239 as 0 for B1, B2 and C1 and 1 for A1/A2; the PC scores it 1 for all five. Cause: the B and C replies use a brute-force recursive enumeration (the A replies use a table DP). The EvalPlus plus-tests include large inputs, and that solution runs about 26 s on this PC against the scorer's 30 s time limit, so on the slower server CPU it timed out. Five repeat timings in the final environment (B1: 25.7-27.1 s; B2: 25.9-27.5 s; C1: 26.0-27.6 s; maximum 27.6 s, margin 2.4 s; A replies 0.2 s) never exceeded the limit. By the 2 s rule it is not flagged, but since the same replies timed out on another machine the item is recorded as **hardware-sensitive**: its B/C result depends on CPU speed. Item kept, scored identically for every session. Qualitative observation (not a finding about capability): on this item the overlay arms chose a far slower algorithm than stock (about 26 s against 0.2 s). Effect size on the code result if it were scored 0 in B/C: -0.28 pp on code, about -0.05 pp on the composite.
3. Every other set's per-item scores are identical between the second host's and the PC scoring in all five sessions (checked item by item for the id sets and the scores of mmlu_pro, math500, code except mbpp-239, mgsm, bfcl, lc, json; Layer 2 token hashes identical).

The scoring code itself is unchanged since the pre-B commit; only the seed wrapper is new. Sensitivity: the headline numbers with the second host's scores instead are in `analysis/extra_results_altenv.json` (see report).

> **Provenance note (added at export, 2026-11-10; the text above is unchanged).** Statements here that scoring code was unchanged must be read together with the D14 provenance correction: after the protocol freeze but before B collection, the IFEval import changed from the installed package to the vendored copy. ## D15 (2026-11-10): historical refusal truncation handling differed from the protocol
